# Supabase Skill (Hub)

Load this skill when the task involves persistence on a site that has Supabase
connected — users, auth, saving, lists, history, admin data, SQL, edge
functions, API keys.

## This is a legacy capability

Supabase is only available on sites that already had it connected before moving
to this template. It cannot be added to a site that does not have it, and there
is no tool to connect it.

What that means while you work:

- If `<services>` shows Supabase, the project has a live Supabase database.
  Build on it. It is the only database — do NOT propose or scaffold a second one.
- Never suggest connecting Supabase, migrating off it, or moving the data
  anywhere. The database stays where it is.
- PocketBase and Integrated AI are not available on these sites. Their enable
  tools are hidden from you. Do not mention them, and do not tell the user to
  turn them on. The PocketBase client and auth helpers the framework-mode
  skill mentions (`@/lib/pocketbase-client`, `@/hooks/use-auth`,
  `@/lib/require-auth`) are not used here.
- Server-side work goes in a Supabase edge function, not a React Router
  `/api/*` resource route. See `supabase/references/EDGE_FUNCTIONS.md`.

## Architecture — the browser talks to Supabase directly

- `apps/web` — React Router framework mode. This is the whole app. Pages are
  server-rendered, then hydrate in the browser.
- The Supabase project — Postgres + auth + storage + edge functions, hosted by
  Supabase and owned by the user.
- `supabase/functions/<name>/index.ts` — edge function source, versioned in
  this repo. Deployed with `deploy_supabase_edge_function`.

**Default flow:** browser → Supabase via the SDK client, from components
(effects, event handlers) or a `clientLoader` / `clientAction`. No server in
the middle for CRUD or auth — Supabase provides both, and Row Level Security
policies on each table are the authorization layer. See
`supabase/references/USING_IN_REACT.md`.

**The session is browser-only.** The server renders every page as a
signed-out visitor, and the published site caches GET responses for everyone.
Never read the session, guard a route, or load per-user data in a server
`loader`. A server `loader` may only read public content that is the same for
every visitor.

**Edge function escape hatch:** add a function only when the work needs a
secret that cannot ship to the browser, a webhook receiver, or server-side
orchestration.

## The client

Already wired up at `apps/web/src/lib/customSupabaseClient.js`:

```js
import { supabase } from "@/lib/customSupabaseClient";
```

The default export and the `customSupabaseClient` named export are the same
client — prefer the `supabase` name for readability.

## The four hard rules

1. **NEVER edit `apps/web/src/lib/customSupabaseClient.js`.** It holds the
   project URL and anon key, is generated by the platform, and is read-only.
   Import it; never rewrite it, never convert it to TypeScript, never create a
   second client, and never hardcode a URL or key anywhere else.

2. **Every edge function MUST import the shared CORS headers.**

   ```ts
   import { corsHeaders } from "./cors.ts";
   ```

   The platform writes `cors.ts` next to the function on deploy, but only when
   the function source contains that import. Without it the browser cannot call
   the function. See `supabase/references/EDGE_FUNCTIONS.md`.

3. **The name in `invoke()` MUST equal the function's directory name.** A
   function at `supabase/functions/send-email/index.ts` is called as
   `supabase.functions.invoke('send-email')`. A mismatch is a 404 at runtime
   and is not caught at build time.

4. **Reuse the tables that already exist.** The current schema is injected as
   `<supabase_schema>`. Read it before writing any SQL. Do not create a
   parallel table when an existing one fits — add a column instead. See
   `supabase/references/CHANGING_THE_DATABASE.md`.

## Schema changes are not revertable

`run_supabase_query` runs SQL against the user's live database. There is no
down migration and no undo — a message revert will not roll the schema back.

Because of that:

- Prefer additive changes. `ADD COLUMN`, new tables, new policies.
- Use `IF NOT EXISTS` / `IF EXISTS` so a re-run is harmless.
- Never `DROP TABLE`, `DROP COLUMN`, `TRUNCATE`, or `DELETE` without the user
  asking for exactly that in this conversation. Deleting a column deletes the
  production data in it.
- Preview and production share one database. There is no separate preview
  data — a row you insert while testing is a real row on the live site, and a
  schema change takes effect on the published site immediately.
- Treat `<supabase_schema>` as a starting map, not a complete definition. It
  omits details such as column defaults, `CHECK` constraints, enum values, and
  function bodies. Inspect those with read-only SQL before writing to an
  existing table or replacing a function; never invent allowed values.
- Validate in small steps: inspect, apply one coherent change, then verify with
  read-only SQL. Do not put setup, many assertions, and cleanup into one large
  fallible block. After a failed mutating query, inspect the live state before
  retrying so leftover test data or a partially applied change is not missed.

## Your three tools

| Tool                           | Use for                                                        |
| ------------------------------ | -------------------------------------------------------------- |
| `run_supabase_query`           | Any SQL — create/alter tables, RLS policies, indexes, seeding  |
| `deploy_supabase_edge_function`| Deploy a function you wrote to `supabase/functions/<name>/index.ts` |
| `set_supabase_secret`          | Store an API key for an edge function to read via `Deno.env`   |

All three act on the live project. Read the matching reference before the first
call in a task.

## Pitfalls that bite every time

- **Editing `customSupabaseClient.js`.** Read-only. Hard rule #1.
- **Creating a second client** with `createClient(...)` in a component, a
  `.server.ts` module, or a new `lib/supabase.ts`. Import the existing one.
- **Querying per-user data or checking auth in a server `loader`.** The server
  has no session and its GET responses are cached for every visitor. Query in
  the browser. See `supabase/references/USING_IN_REACT.md`.
- **Using the PocketBase auth helpers** (`@/hooks/use-auth`, `requireAuth`).
  Auth is `@/contexts/SupabaseAuthContext`. See `supabase/references/AUTH.md`.
- **Forgetting `corsHeaders`** in an edge function, or forgetting to answer the
  `OPTIONS` preflight. The function works from curl and fails from the browser.
- **`invoke('sendEmail')` for a function directory named `send-email`.** 404.
- **Creating a new table when `<supabase_schema>` already has one that fits.**
  Read the injected schema first.
- **Inserting into a table with RLS enabled and no policy.** The insert fails
  silently from the browser's point of view — the error is in the response, not
  an exception. Every new table needs its policies in the same SQL statement
  that creates it. See `supabase/references/CHANGING_THE_DATABASE.md`.
- **Putting an API key in frontend code, in `apps/web/.env`, or in a `/api/*`
  route.** Secrets belong in `set_supabase_secret` and are read inside an edge
  function. See `supabase/references/SECRETS.md`.
- **Suggesting PocketBase or Integrated AI.** Not available on these sites.
- **Using `localStorage` as the database.** The site has a real Postgres
  database. localStorage lives in one browser and vanishes on another device.
- **Reaching for a migration file.** There is no migration runner here. Schema
  changes are SQL through `run_supabase_query`, not files on disk.
